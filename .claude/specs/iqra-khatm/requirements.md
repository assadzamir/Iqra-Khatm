# Requirements: iqra-khatm

> Generated by spec-engine v1.0.0

## Overview

Iqra Khatm is a React Native Expo SDK 54 Islamic app for collaborative Quran reading (khatm). The **Group Khatm feature is already fully implemented** (see `.claude/specs/group-khatm/`). This spec adds three new feature areas that integrate with the existing codebase:

1. **User Authentication** — email+password and phone/OTP signup/login via Supabase Auth, with display name onboarding
2. **Quran Reader Screen** — page-by-page Quran reading with Arabic text from a remote API, bookmarks, font/theme settings, translation toggle, and khatm auto-tracking integration
3. **Email Notifications** — Resend API email delivery from a Supabase Edge Function, running in parallel with existing Expo push notifications

The existing database (migrations 001-004), Supabase client, MMKV storage, Zustand store, khatm types/constants, auto-tracking hook, and notification-scheduler Edge Function remain unchanged except where explicitly extended.

## Depends On

- group-khatm (already implemented — auth, reader, and email features integrate with it)

## Lessons Applied

The following lessons from `.claude/specs/lessons.json` directly influenced these requirements:

- **Lesson 1 (RLS/RPC at design time)**: Every new write path (bookmarks, email preferences, user profiles) specifies its RLS policy or RPC in the acceptance criteria.
- **Lesson 3 (Audit log INSERT policy)**: New tables that receive client writes include explicit INSERT RLS policies.
- **Lesson 4 (Persistent queues)**: Bookmark offline queue uses MMKV, not in-memory storage.
- **Lesson 5 (Atomic RPCs)**: Signup + profile creation is a single atomic flow, not separate client calls.
- **Lesson 6 (Large screen splitting)**: The Quran Reader screen is decomposed into sub-components (toolbar, page renderer, navigation bar, bookmark sheet) to keep each under 300 lines.

## User Stories

### US-1: Email + Password Signup

**As a** new user
**I want** to create an account with my email and a password
**So that** I can access Khatm groups and the Quran reader

#### Acceptance Criteria (EARS Notation)

1. WHEN the user submits a valid email address and a password of 8 or more characters on the signup screen
   THE SYSTEM SHALL create a Supabase Auth account and send a confirmation email to the provided address

2. ~~WHEN the user submits a signup form with an email already registered in Supabase Auth
   THE SYSTEM SHALL display the message "An account with this email already exists" and not create a duplicate account~~
   **Superseded by AC-7** — revealing email existence enables enumeration. AC-7 governs: a uniform message is shown regardless of whether the email is registered.

3. WHEN the user submits a signup form with a password shorter than 8 characters
   THE SYSTEM SHALL display the message "Password must be at least 8 characters" and not submit the form

4. WHEN the user submits a signup form with an invalid email format
   THE SYSTEM SHALL display the message "Enter a valid email address" and not submit the form

5. [inferred] WHEN the Supabase Auth API returns a network error during signup
   THE SYSTEM SHALL display the message "Connection error. Check your internet and try again."

6. [inferred] WHILE the signup request is in progress
   THE SYSTEM SHALL display a loading indicator on the submit button and disable the button to prevent duplicate submissions

7. [threat-model] THE SYSTEM SHALL return a generic message on signup for both new and existing email addresses to prevent email enumeration, OR THE SYSTEM SHALL implement a confirmation-first flow where account existence is not revealed until email is verified (HIGH)

### US-2: Email + Password Login

**As a** returning user
**I want** to log in with my email and password
**So that** I can access my Khatm groups and reading history

#### Acceptance Criteria (EARS Notation)

1. WHEN the user submits a valid email and correct password on the login screen
   THE SYSTEM SHALL authenticate via Supabase Auth, store the session, and navigate to the Home tab

2. WHEN the user submits a login form with an incorrect email or password
   THE SYSTEM SHALL display the message "Invalid email or password" without revealing which field was wrong

3. WHEN the user taps "Forgot password?" on the login screen
   THE SYSTEM SHALL navigate to the forgot password screen

4. WHEN the user submits a valid email on the forgot password screen
   THE SYSTEM SHALL call Supabase Auth `resetPasswordForEmail` and display the message "Password reset email sent. Check your inbox."

5. WHEN the user submits a forgot password request for an email not found in Supabase Auth
   THE SYSTEM SHALL display the same "Password reset email sent" message (to prevent user enumeration)

6. [inferred] WHEN the Supabase Auth API returns a network error during login
   THE SYSTEM SHALL display the message "Connection error. Check your internet and try again."

7. [threat-model] WHEN five consecutive failed login attempts occur for the same email within 15 minutes THE SYSTEM SHALL display a message indicating temporary lockout and reject further attempts until the window expires (enforced by Supabase Auth rate limits or client-side throttle) (MEDIUM)

8. [threat-model] WHEN the user signs out THE SYSTEM SHALL clear the AuthStore session and profile state, invalidate all TanStack Query caches, and clear any pending bookmark operations from MMKV to prevent stale session data reuse (CRITICAL)

9. [threat-model] WHEN a Supabase Auth login attempt fails THE SYSTEM SHALL log the failure event type and timestamp to the client-side console (non-PII) for debugging, and the email-notifications Edge Function SHALL log all send failures with event type and participant_id to khatm_audit_log for non-repudiation (MEDIUM)

### US-3: Phone + OTP Login

**As a** user who prefers phone-based authentication
**I want** to log in or sign up with my phone number and a one-time SMS code
**So that** I can access the app without needing an email account

#### Acceptance Criteria (EARS Notation)

1. WHEN the user submits a valid phone number (E.164 format) on the OTP screen
   THE SYSTEM SHALL call Supabase Auth `signInWithOtp({ phone })` and navigate to the OTP verification input

2. WHEN the user enters the correct 6-digit OTP code within 60 seconds of receiving it
   THE SYSTEM SHALL verify the OTP via Supabase Auth, store the session, and navigate to the Home tab (or onboarding if first login)

3. WHEN the user enters an incorrect or expired OTP code
   THE SYSTEM SHALL display the message "Invalid or expired code. Request a new one."

4. WHEN the user submits a phone number in an invalid format
   THE SYSTEM SHALL display the message "Enter a valid phone number with country code (e.g., +1234567890)"

5. [inferred] THE SYSTEM SHALL NOT allow more than 3 OTP requests per phone number within a 10-minute window (enforced by Supabase Auth rate limits)

6. [inferred] WHEN the 60-second OTP timer expires
   THE SYSTEM SHALL enable a "Resend code" button on the OTP verification screen

### US-4: Display Name Onboarding

**As a** first-time user who just signed up
**I want** to set my display name
**So that** other Khatm group members can identify me

#### Acceptance Criteria (EARS Notation)

1. IF the authenticated user has no `display_name` set in `user_profiles`
   WHEN the user completes authentication
   THE SYSTEM SHALL navigate to the onboarding screen before allowing access to the main app

2. WHEN the user submits a display name between 2 and 50 characters on the onboarding screen
   THE SYSTEM SHALL insert a row into `user_profiles` with the user's `auth.uid()` and the provided name, then navigate to the Home tab

3. WHEN the user submits a display name shorter than 2 characters or longer than 50 characters
   THE SYSTEM SHALL display the message "Display name must be between 2 and 50 characters"

4. THE SYSTEM SHALL NOT allow navigation past the onboarding screen until a valid display name is saved

5. [inferred] WHEN the user_profiles insert fails due to a network error
   THE SYSTEM SHALL display the message "Could not save your name. Check your connection and try again." and keep the user on the onboarding screen

### US-5: Quran Page Rendering

**As a** user
**I want** to read the Quran page by page with Arabic text
**So that** I can read the Quran within the app

#### Acceptance Criteria (EARS Notation)

1. WHEN the user opens the Quran reader at page N (where N is between 1 and 604)
   THE SYSTEM SHALL fetch the Arabic verse text for page N from the alquran.cloud API endpoint `GET https://api.alquran.cloud/v1/page/{pageNumber}/quran-uthmani` and render the verses in the correct order

2. WHEN the alquran.cloud API request for page N succeeds
   THE SYSTEM SHALL cache the response using TanStack Query with a `staleTime` of 24 hours to avoid redundant network requests

3. WHEN the alquran.cloud API request for page N fails with a network error
   THE SYSTEM SHALL display an inline error message "Could not load this page. Tap to retry." with a retry button

4. WHILE the API request for a Quran page is in progress
   THE SYSTEM SHALL display a centered loading spinner within the page area

5. THE SYSTEM SHALL display the Surah name and Juz number in the page header for the current page

6. [inferred] WHEN the alquran.cloud API returns an HTTP 429 (rate limit) response
   THE SYSTEM SHALL wait 2 seconds and automatically retry the request once before showing the error message

7. [threat-model] WHEN the Quran API client makes a fetch request to alquran.cloud THE SYSTEM SHALL enforce a 10-second request timeout using AbortController to prevent hung connections (HIGH)

8. [threat-model] WHEN the QuranReaderPage receives a page parameter from the URL THE SYSTEM SHALL validate it is an integer between 1 and 604 and redirect to page 1 if invalid (HIGH)

### US-6: Quran Page Navigation

**As a** user
**I want** to navigate between Quran pages using next/previous controls and jump to a specific Juz
**So that** I can read sequentially or jump to a section of interest

#### Acceptance Criteria (EARS Notation)

1. WHEN the user taps the "Next" button while on a page less than 604
   THE SYSTEM SHALL navigate to page N+1 using expo-router `router.replace`

2. WHEN the user taps the "Previous" button while on a page greater than 1
   THE SYSTEM SHALL navigate to page N-1 using expo-router `router.replace`

3. WHILE the user is on page 1
   THE SYSTEM SHALL disable the "Previous" button

4. WHILE the user is on page 604
   THE SYSTEM SHALL disable the "Next" button

5. WHEN the user taps the Juz selector and chooses Juz K (1-30)
   THE SYSTEM SHALL navigate to the `startPage` for Juz K as defined in `JUZ_PAGE_RANGES`

6. [inferred] WHEN the user swipes left on the page content area
   THE SYSTEM SHALL navigate to the next page (equivalent to tapping "Next")

7. [inferred] WHEN the user swipes right on the page content area
   THE SYSTEM SHALL navigate to the previous page (equivalent to tapping "Previous")

### US-7: Quran Reader Settings (Font Size and Theme)

**As a** user
**I want** to adjust font size and color theme in the Quran reader
**So that** I can read comfortably in different conditions

#### Acceptance Criteria (EARS Notation)

1. WHEN the user selects a font size (small: 18px, medium: 24px, large: 32px) from the settings toolbar
   THE SYSTEM SHALL re-render the Arabic text at the selected font size and persist the choice in MMKV under the key `quran-reader-font-size`

2. WHEN the user selects a theme (light, dark, sepia) from the settings toolbar
   THE SYSTEM SHALL apply the selected background and text colors and persist the choice in MMKV under the key `quran-reader-theme`

3. WHEN the user reopens the Quran reader after closing it
   THE SYSTEM SHALL restore the previously saved font size and theme from MMKV

4. [inferred] IF no font size or theme preference exists in MMKV
   WHEN the user opens the Quran reader for the first time
   THE SYSTEM SHALL default to medium (24px) font size and the system color scheme (light or dark)

### US-8: Translation Toggle

**As a** user
**I want** to show or hide an English translation below each verse
**So that** I can understand the meaning while reading Arabic text

#### Acceptance Criteria (EARS Notation)

1. WHEN the user enables the translation toggle in the reader toolbar
   THE SYSTEM SHALL fetch the English translation for the current page from `GET https://api.alquran.cloud/v1/page/{pageNumber}/en.asad` and display each English verse below its corresponding Arabic verse

2. WHEN the user disables the translation toggle
   THE SYSTEM SHALL hide all English translation text and display only Arabic verses

3. WHEN the translation API request fails
   THE SYSTEM SHALL display the message "Translation unavailable" below the toggle and continue showing Arabic text

4. THE SYSTEM SHALL persist the translation toggle state in MMKV under the key `quran-reader-translation-on` so it is restored on next open

5. [inferred] WHEN the translation is enabled and the user navigates to a new page
   THE SYSTEM SHALL fetch the translation for the new page without requiring the user to re-enable the toggle

### US-9: Bookmarks

**As a** user
**I want** to bookmark a Quran page so I can return to it later
**So that** I can resume reading where I left off

#### Acceptance Criteria (EARS Notation)

1. WHEN the user taps the bookmark icon on page N
   THE SYSTEM SHALL insert a row into `user_bookmarks` (user_id = auth.uid(), page_number = N) and display a filled bookmark icon

2. WHEN the user taps the filled bookmark icon on a bookmarked page
   THE SYSTEM SHALL delete the corresponding row from `user_bookmarks` and display an unfilled bookmark icon

3. WHEN the user opens the bookmarks list (accessible from the reader toolbar)
   THE SYSTEM SHALL query `user_bookmarks` for the authenticated user ordered by `created_at DESC` and display each bookmark with the page number and Surah name

4. WHEN the user taps a bookmark in the bookmarks list
   THE SYSTEM SHALL navigate the reader to that page number

5. WHEN the bookmark insert or delete fails due to a network error
   THE SYSTEM SHALL toggle the icon optimistically, queue the write in MMKV under the key `pending-bookmark-ops`, and retry on the next successful API call

6. [inferred] THE SYSTEM SHALL NOT allow duplicate bookmarks for the same user and page (enforced by UNIQUE constraint on user_id + page_number)

7. [threat-model] WHEN the useBookmarks hook replays pending offline bookmark operations from MMKV THE SYSTEM SHALL verify the current authenticated user ID matches the user_id in each queued operation and discard mismatched entries (HIGH)

8. [threat-model] THE SYSTEM SHALL limit the bookmarks list query to a maximum of 200 results to prevent unbounded memory consumption on the client (MEDIUM)

### US-10: Khatm Auto-Tracking Integration

**As a** Khatm participant
**I want** the Quran reader to automatically track my reading progress for my assigned Juz
**So that** I do not need to manually update my progress

#### Acceptance Criteria (EARS Notation)

1. WHERE the Quran reader is opened via the khatm "Start Reading" action (activeReadingContext is non-null in the Zustand store)
   WHEN the user navigates pages within their assigned Juz range
   THE SYSTEM SHALL invoke the existing `useAutoTracking` hook which writes progress to `khatm_juz_assignments` every 2+ pages and on reader exit

2. WHERE the Quran reader is opened without a khatm context (activeReadingContext is null)
   WHEN the user navigates pages
   THE SYSTEM SHALL NOT invoke the auto-tracking hook or write any khatm progress

3. WHERE a khatm reading context is active
   THE SYSTEM SHALL display a banner at the top of the reader showing "Reading Juz {N} for {group title}"

4. [inferred] WHERE a khatm reading context is active and the user navigates outside the assigned Juz page range
   WHEN the user reaches a page outside the `startPage`-`endPage` range
   THE SYSTEM SHALL display a toast message "You've left your assigned Juz range" but allow continued navigation

### US-11: Email Notification Delivery

**As a** Khatm group participant who has provided an email address
**I want** to receive email reminders about my Khatm progress
**So that** I stay on track even if I miss push notifications

#### Acceptance Criteria (EARS Notation)

1. WHEN the existing `notification-scheduler` Edge Function fires for a deadline reminder, stall reminder, not-started reminder, or completion celebration
   THE SYSTEM SHALL also invoke the `email-notifications` Edge Function to send an email for the same event to participants who have a non-null `email` field in `khatm_participants`

2. WHEN the `email-notifications` Edge Function is invoked with a valid recipient email and event type
   THE SYSTEM SHALL call the Resend API `POST https://api.resend.com/emails` with a bilingual HTML body (Arabic header, English body) containing the group name, participant name, and a relevant call-to-action deep link

3. WHEN the Resend API returns a non-2xx response
   THE SYSTEM SHALL log the failure to `khatm_audit_log` with `action_type = 'EMAIL_FAILED'` and retry once after 3 seconds

4. IF a participant has a null `email` field in `khatm_participants`
   WHEN the email notification function processes that participant
   THE SYSTEM SHALL skip them without logging an error

5. THE SYSTEM SHALL NOT send more than one email per event type per participant per day (deduplication via `khatm_audit_log` check, same pattern as existing push dedup)

6. [threat-model] WHEN the notification-scheduler invokes the email-notifications Edge Function and the call fails THE SYSTEM SHALL NOT block or delay the existing push notification pipeline (MEDIUM)

### US-12: Email Unsubscribe

**As a** Khatm group participant
**I want** to unsubscribe from email notifications with one click
**So that** I can stop receiving emails without contacting an administrator

#### Acceptance Criteria (EARS Notation)

1. THE SYSTEM SHALL include an unsubscribe URL in every email notification footer

2. WHEN a user clicks the unsubscribe URL containing a valid signed JWT
   THE SYSTEM SHALL set `email_notifications_enabled = false` on the corresponding `khatm_participants` row and display a confirmation page

3. WHEN a user clicks an unsubscribe URL containing an invalid or expired JWT
   THE SYSTEM SHALL display the message "This link has expired. Open the app to manage your notification preferences."

4. IF `email_notifications_enabled` is false for a participant
   WHEN the email notification function processes that participant
   THE SYSTEM SHALL skip them without sending an email

5. [inferred] WHEN the user opens the app's notification settings
   THE SYSTEM SHALL display the current `email_notifications_enabled` state and allow toggling it on or off

6. [threat-model] WHEN the email-unsubscribe Edge Function receives a JWT THE SYSTEM SHALL validate the `iss` and `aud` claims match the application's Supabase project before processing the unsubscribe request (CRITICAL)

### US-13: Email Content and Formatting

**As a** Khatm group participant receiving email notifications
**I want** the emails to be clear, bilingual, and actionable
**So that** I understand what action to take

#### Acceptance Criteria (EARS Notation)

1. THE SYSTEM SHALL format every notification email with: an Arabic Bismillah header, the group name, the participant's display name, an English body describing the event, and a deep link CTA button

2. THE SYSTEM SHALL use the following subject lines per event type:
   - Deadline reminder: "Reminder: {group_name} ends in {N} days"
   - Stall reminder: "Your Juz {N} reading has paused"
   - Not-started reminder: "Time to start Juz {N}"
   - Completion celebration: "Alhamdulillah! {group_name} is complete"

3. THE SYSTEM SHALL set the `From` address to `notifications@iqra-app.com` (or the configured Resend verified domain)

4. [inferred] THE SYSTEM SHALL include the `List-Unsubscribe` header in every email per RFC 2369 to support one-click unsubscribe in email clients

## Non-Functional Requirements

### Performance

1. THE SYSTEM SHALL render a Quran page (from cached data) within 100 milliseconds of navigation
2. THE SYSTEM SHALL complete the initial Quran page API fetch (uncached) within 3 seconds for the 95th percentile on a 3G connection
3. THE SYSTEM SHALL complete Supabase Auth login in under 2 seconds for the 95th percentile
4. [inferred] THE SYSTEM SHALL prefetch the next and previous Quran pages while the user reads the current page, so navigation feels instant

### Security

5. THE SYSTEM SHALL store Supabase Auth session tokens using Supabase's built-in secure storage adapter, not in plaintext MMKV
6. THE SYSTEM SHALL enforce RLS on `user_bookmarks` so users can only read and write their own bookmarks
7. THE SYSTEM SHALL enforce RLS on `user_profiles` so users can only read and update their own profile
8. [inferred] THE SYSTEM SHALL validate all phone number inputs against E.164 format on the client before sending to Supabase Auth

### Accessibility

9. THE SYSTEM SHALL support right-to-left text direction for all Arabic content in the Quran reader
10. THE SYSTEM SHALL ensure all interactive elements (buttons, toggles, bookmark icons) have a minimum touch target of 44x44 points
11. [inferred] THE SYSTEM SHALL provide `accessibilityLabel` properties on all Quran reader controls for screen reader compatibility

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| alquran.cloud API rate limiting or downtime blocks Quran reading | Medium | High | Cache aggressively (24h staleTime); show cached pages offline; document fallback to quran.com API |
| Supabase Auth phone OTP SMS delivery unreliable in certain regions | Medium | Medium | Provide email+password as an always-available alternative; display clear error messaging |
| Resend API key leak in Edge Function environment variables | Low | High | Store key in Supabase Vault (encrypted secrets); never log the key; rotate quarterly |
| Email deliverability — notifications land in spam | Medium | Medium | Configure SPF, DKIM, DMARC for the sending domain; use Resend's managed deliverability features |
| Large Arabic font rendering performance on low-end Android devices | Medium | Medium | Limit max font size to 32px; test on low-end Android (2GB RAM); use FlatList for verse list if > 20 verses per page |
| No root `_layout.tsx` exists — adding auth gate may break existing navigation | Low | High | Create `src/app/_layout.tsx` as Wave 0 task; test that existing (tabs) and (quran-reader) routes still work |
| Bookmark sync conflicts when offline queue replays stale operations | Low | Low | Use MMKV-backed queue with timestamps; server-side UNIQUE constraint prevents duplicates; upsert on conflict |

## Security Context

### Detected Categories and Applied Criteria

**API Endpoints** — the email-notifications Edge Function is an HTTP handler:

- 1. [security] THE SYSTEM SHALL NOT process requests to the `email-notifications` Edge Function without first verifying a valid Supabase service-role or cron-invocation token
- 2. [security] THE SYSTEM SHALL NOT accept more than 60 requests per minute to the `email-notifications` Edge Function endpoint

**Data Storage** — new tables `user_bookmarks`, `user_profiles`; new columns on `khatm_participants` (`email_notifications_enabled`):

- 3. [security] THE SYSTEM SHALL NOT store auth session tokens in plaintext — secure storage is required
- 4. [security] THE SYSTEM SHALL NOT allow any user to read or modify another user's `user_bookmarks` or `user_profiles` rows without explicit RLS verification

**External Integrations** — alquran.cloud API, Resend API:

- 5. [security] WHEN connecting to the Resend API THE SYSTEM SHALL verify the TLS certificate is valid and not self-signed
- 6. [security] WHEN connecting to alquran.cloud THE SYSTEM SHALL use HTTPS exclusively

**User Input Handling** — email, phone number, display name, page number inputs:

- 7. [security] THE SYSTEM SHALL NOT pass display name or email input to the database without parameterized queries
- 8. [security] THE SYSTEM SHALL NOT render user-provided display names in email HTML without HTML entity escaping

**Baseline (always applied)**:

- 9. [security] THE SYSTEM SHALL NOT expose internal error details (stack traces, file paths, database error messages) in user-facing output
