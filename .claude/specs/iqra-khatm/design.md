## Codebase Context (Verified Interfaces)

The following types, files, and schemas were verified by reading the actual source files:

**Supabase client** — `src/lib/supabase.ts`: exports `supabase` (createClient with `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`). No auth storage adapter configured — needs adding.

**MMKV adapter** — `src/lib/mmkv.ts`: exports `mmkvStorage` implementing Zustand `StateStorage` interface (`getItem`, `setItem`, `removeItem`).

**Khatm store** — `src/features/khatm/store.ts`: Zustand store `useKhatmStore` with `activeReadingContext: KhatmReadingContext | null` (ephemeral), `activeGroupId: string | null` (persisted to MMKV). Uses `persist` middleware with `partialize`.

**KhatmReadingContext** — `src/features/khatm/types.ts`: `{ groupId: string; participantId: string; juzNumber: number; startPage: number; endPage: number }`.

**JUZ_PAGE_RANGES** — `src/features/khatm/constants.ts`: `Record<number, { startPage: number; endPage: number }>` — 30 entries mapping Juz 1-30 to Mushaf pages 1-604.

**useAutoTracking** — `src/features/khatm/hooks/useAutoTracking.ts`: accepts `{ khatmContext: KhatmReadingContext; currentPage: number; assignmentId: string }`. Writes progress every 2+ pages and on unmount. Uses MMKV queue for failed writes.

**Existing [page].tsx placeholder** — `src/app/(quran-reader)/[page].tsx`: reads `page` from `useLocalSearchParams`, renders `KhatmAutoTracker` conditionally. Currently displays only `<Text>Page {currentPage}</Text>`.

**Database schema** — `supabase/migrations/001_khatm_schema.sql`: `khatm_participants` has `contact_type varchar(20)` and `contact_value varchar(255)` but no dedicated `email` column or `email_notifications_enabled`. `push_token TEXT` was added in migration 004.

**notification-scheduler Edge Function** — `supabase/functions/notification-scheduler/index.ts`: processes deadline reminders, JUZ_NOT_STARTED, JUZ_STALLED. Uses `dispatchNotification()` which calls Expo push API. Deduplicates via `khatm_audit_log`.

**No root _layout.tsx exists** — `src/app/_layout.tsx` does not exist. expo-router needs this file for the root layout. Currently only `src/app/(tabs)/_layout.tsx` exists.

**Package dependencies confirmed**: `@supabase/supabase-js ^2.49.4`, `@tanstack/react-query ^5.74.4`, `zustand ^5.0.3`, `react-native-mmkv ^3.2.0`, `expo ~54.0.0`, `expo-router ~6.0.23`.

## Data Models

### user_profiles (new table)

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | uuid | PK, REFERENCES auth.users(id) ON DELETE CASCADE | Same as Supabase Auth user ID |
| display_name | varchar(50) | NOT NULL, CHECK (length >= 2) | User's chosen display name |
| created_at | timestamptz | NOT NULL DEFAULT now() | Row creation timestamp |
| updated_at | timestamptz | NOT NULL DEFAULT now() | Last update timestamp |

**RLS Policies:**
- SELECT: `auth.uid() = id` (users read their own profile)
- INSERT: `auth.uid() = id` (users create their own profile)
- UPDATE: `auth.uid() = id` (users update their own profile)

### user_bookmarks (new table)

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | uuid | PK DEFAULT gen_random_uuid() | Row ID |
| user_id | uuid | NOT NULL, REFERENCES auth.users(id) ON DELETE CASCADE | Bookmark owner |
| page_number | smallint | NOT NULL, CHECK (page_number BETWEEN 1 AND 604) | Mushaf page number |
| created_at | timestamptz | NOT NULL DEFAULT now() | When bookmark was created |

**Unique constraint:** `UNIQUE (user_id, page_number)` — prevents duplicate bookmarks.

**RLS Policies:**
- SELECT: `auth.uid() = user_id`
- INSERT: `auth.uid() = user_id` (WITH CHECK)
- DELETE: `auth.uid() = user_id`

**Index:** `CREATE INDEX idx_user_bookmarks_user ON user_bookmarks(user_id);`

### khatm_participants (ALTER — add columns)

| New Field | Type | Constraints | Description |
|-----------|------|-------------|-------------|
| email | varchar(255) | NULL | Participant's email for email notifications |
| email_notifications_enabled | boolean | NOT NULL DEFAULT true | Whether email notifications are active |

These columns are nullable-safe: existing rows default to `email = NULL` (no emails sent) and `email_notifications_enabled = true`.

## API Contracts

### alquran.cloud — Quran Page (External API)

- **Covers**: US-5 AC-1
- **Endpoint**: `GET https://api.alquran.cloud/v1/page/{pageNumber}/quran-uthmani`
- **Request**: Path parameter `pageNumber` (1-604), no authentication required
- **Response (200)**:
  ```json
  {
    "code": 200,
    "status": "OK",
    "data": {
      "number": 1,
      "ayahs": [
        {
          "number": 1,
          "text": "بِسْمِ اللَّهِ الرَّحْمَـٰنِ الرَّحِيمِ",
          "numberInSurah": 1,
          "juz": 1,
          "page": 1,
          "surah": {
            "number": 1,
            "name": "سُورَةُ ٱلْفَاتِحَةِ",
            "englishName": "Al-Faatiha"
          }
        }
      ],
      "spiara": { "number": 1 },
      "edition": { "identifier": "quran-uthmani" }
    }
  }
  ```
- **Response (400/404)**: `{ "code": 400, "status": "Bad Request", "data": "..." }`

**Design decision**: alquran.cloud is chosen over quran.com because:
1. Free with no API key required
2. Stable REST API with Uthmani script support
3. Multiple translation editions available
4. No rate limit for reasonable usage (< 100 req/min)

If alquran.cloud becomes unavailable, the API client can be swapped to quran.com's v4 API (`GET https://api.quran.com/api/v4/quran/verses/uthmani?page_number=N`) which requires an API key.

### alquran.cloud — Translation Page (External API)

- **Covers**: US-8 AC-1
- **Endpoint**: `GET https://api.alquran.cloud/v1/page/{pageNumber}/en.asad`
- **Request**: Same pattern as above
- **Response**: Same structure, `text` field contains English translation

### Resend — Send Email (External API)

- **Covers**: US-11 AC-2
- **Endpoint**: `POST https://api.resend.com/emails`
- **Request**:
  ```json
  {
    "from": "Iqra Khatm <notifications@iqra-app.com>",
    "to": ["recipient@example.com"],
    "subject": "Reminder: My Khatm Group ends in 2 days",
    "html": "<html>...</html>",
    "headers": {
      "List-Unsubscribe": "<https://project-ref.supabase.co/functions/v1/email-unsubscribe?token=...>"
    }
  }
  ```
- **Response (200)**: `{ "id": "email_id" }`
- **Response (4xx/5xx)**: `{ "statusCode": 422, "message": "..." }`

### Email Notifications Edge Function (Internal API)

- **Covers**: US-11 AC-1, AC-2
- **Endpoint**: `POST /functions/v1/email-notifications`
- **Auth**: `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` (called only by notification-scheduler, not by clients)
- **Request**: `EmailNotificationRequest` (see C-18 interface above)
- **Response (200)**: `EmailNotificationResponse`

### Email Unsubscribe Edge Function (Internal API)

- **Covers**: US-12 AC-2, AC-3
- **Endpoint**: `GET /functions/v1/email-unsubscribe?token=<jwt>`
- **Auth**: JWT in query parameter (self-verifying)
- **Response (200)**: HTML page "You have been unsubscribed"
- **Response (400/401)**: HTML page with expired link message

## Error Handling Strategy

### Error Taxonomy

| Error Class | Source | User-Facing Message | HTTP Status | Recovery |
|------------|--------|---------------------|-------------|----------|
| Validation | Client form input | Specific field errors (see ACs) | N/A (client-side) | Fix input and resubmit |
| AuthError | Supabase Auth | "Invalid email or password" / OTP messages | 401 | Re-enter credentials |
| NetworkError | fetch / Supabase client | "Connection error. Check your internet and try again." | N/A | Retry or queue |
| QuranAPIError | alquran.cloud 4xx/5xx | "Could not load this page. Tap to retry." | 400-500 | Tap retry button |
| RateLimitError | alquran.cloud 429 | Auto-retry once after 2s, then show error | 429 | Wait and retry |
| BookmarkConflict | Supabase UNIQUE violation | Silent (optimistic UI already correct) | 409 | Ignore (idempotent) |
| ResendError | Resend API | N/A (server-side, logged to audit) | 4xx/5xx | Auto-retry once after 3s |
| JWTError | Unsubscribe handler | "This link has expired..." | 401 | Open app to manage preferences |

### Error Propagation

- **Frontend (React Native)**: Errors are caught in TanStack Query `onError` callbacks or try/catch in mutation handlers. User-facing messages are displayed via inline `<Text>` elements or toast notifications. No error boundaries for now — individual component error states suffice.
- **API Layer (alquran.cloud)**: The `quranApi.ts` client wraps `fetch` and throws typed errors. TanStack Query handles retries (1 retry for 429, 0 retries for other errors).
- **Service Layer (Supabase)**: Supabase client errors are caught and mapped to user-facing messages in hook `onError` handlers. Auth errors use Supabase's error codes (`AuthApiError`, `AuthWeakPasswordError`).
- **Data Layer (Edge Functions)**: Edge Functions log full error details to `khatm_audit_log` and return sanitized JSON responses. Stack traces are never included in HTTP responses.

## State Management

### Auth State

| State | Trigger | Next States | Side Effects |
|-------|---------|-------------|--------------|
| Initializing | App launch | Authenticated, Unauthenticated | Read session from Supabase storage |
| Unauthenticated | No session found / signOut | Authenticated | Show auth screens |
| Authenticated | Successful login/signup | NeedsOnboarding, Ready | Store session, check profile |
| NeedsOnboarding | Auth success + no profile | Ready | Show onboarding screen |
| Ready | Profile exists | Unauthenticated (on signOut) | Show main app |

### Auth State Storage

- **Where**: Supabase Auth manages session persistence internally (with AsyncStorage or custom adapter). `useAuthStore` (Zustand, non-persisted) holds the reactive session/profile state for UI.
- **Persistence**: Session survives app restart (Supabase Auth handles this). Profile is re-fetched on session restore.
- **Sync**: `supabase.auth.onAuthStateChange()` listener in `_layout.tsx` keeps Zustand store in sync.

### Reader Settings State

| State | Trigger | Next States | Side Effects |
|-------|---------|-------------|--------------|
| Default | First open, no MMKV keys | Custom | Use medium/system-theme/no-translation |
| Custom | User changes setting | Custom | Write to MMKV, re-render |

### Reader Settings Storage

- **Where**: MMKV (3 keys: `quran-reader-font-size`, `quran-reader-theme`, `quran-reader-translation-on`)
- **Persistence**: Survives app restart and logout (reader settings are device-level, not user-level)
- **Sync**: No backend sync — MMKV only

## Quran API Design Decision

**Recommended**: alquran.cloud (https://alquran.cloud/api)

| Criterion | alquran.cloud | quran.com v4 |
|-----------|---------------|--------------|
| API Key | Not required | Required (free tier) |
| Rate Limit | Generous (undocumented, ~100/min works) | 50 req/min |
| Uthmani Script | Yes (`quran-uthmani` edition) | Yes |
| Page-based endpoint | `GET /v1/page/{N}/{edition}` | `GET /v4/quran/verses/uthmani?page_number=N` |
| Translation editions | 100+ editions | 100+ editions |
| Response shape | Flat ayahs array with surah info | Nested, requires pagination handling |
| Reliability | High (CDN-backed, years of uptime) | High |

**Rationale**: alquran.cloud requires no API key, has a simpler response shape for page-based queries, and supports the `quran-uthmani` edition directly. The trade-off is no official SLA, mitigated by aggressive caching (24h staleTime in TanStack Query).

## Alternatives Considered

### Quran Data Source: Local JSON bundle vs Remote API

- **Description**: Bundle all 604 pages of Quran text as a JSON file in the app bundle (~5MB compressed)
- **Pros**: No network dependency, instant page loads, works fully offline
- **Cons**: Increases app bundle size by ~5MB; translation updates require app release; legal/licensing concerns with bundling Quran text
- **Why rejected**: Remote API chosen for smaller bundle, easier translation edition switching, and avoidance of Quran text licensing issues. Offline support can be added later as a download-on-demand feature.

### Auth: Custom auth vs Supabase Auth

- **Description**: Build custom email/password and OTP auth with bcrypt and Twilio directly
- **Pros**: Full control over auth flow
- **Cons**: Significant security surface to maintain; session management, token refresh, rate limiting all need custom implementation
- **Why rejected**: Supabase Auth is already integrated (existing RLS uses `auth.uid()`), battle-tested, and free. No reason to reimplement.

### Email: SendGrid vs Resend

- **Description**: Use SendGrid instead of Resend for email delivery
- **Pros**: More established, higher free tier (100 emails/day)
- **Cons**: Heavier SDK, more complex API, less developer-friendly
- **Why rejected**: Resend has a simpler API, better Deno compatibility for Edge Functions, and sufficient free tier (100 emails/day on free plan). Both have comparable deliverability.

### Bookmark Storage: MMKV-only vs Supabase

- **Description**: Store bookmarks only in MMKV (device-local), no server sync
- **Pros**: Simpler, no RLS needed, instant
- **Cons**: Bookmarks lost on device change or app reinstall; no cross-device sync
- **Why rejected**: Users expect bookmarks to persist across devices. Supabase storage with MMKV optimistic queue provides the best UX.

## Migration Plan

### Database Migration: `supabase/migrations/005_auth_reader_email.sql`

**New tables:**
- `user_profiles` (id, display_name, created_at, updated_at) with RLS
- `user_bookmarks` (id, user_id, page_number, created_at) with RLS

**ALTER existing table:**
- `khatm_participants`: ADD COLUMN `email varchar(255) NULL`
- `khatm_participants`: ADD COLUMN `email_notifications_enabled boolean NOT NULL DEFAULT true`

**RLS policies:**
- user_profiles: SELECT/INSERT/UPDATE where `auth.uid() = id`
- user_bookmarks: SELECT/INSERT/DELETE where `auth.uid() = user_id`

**No data backfilling required** — new tables start empty; new columns have safe defaults.

**Backward compatibility**: Existing khatm features are unaffected. The `email` column is nullable, so existing rows without emails simply receive no email notifications. The `email_notifications_enabled` defaults to `true`, so participants who later add an email will receive notifications by default.

**Rollback plan**:
1. Drop RLS policies on new tables
2. `DROP TABLE user_bookmarks;`
3. `DROP TABLE user_profiles;`
4. `ALTER TABLE khatm_participants DROP COLUMN email, DROP COLUMN email_notifications_enabled;`

### Supabase Client Modification: `src/lib/supabase.ts`

Add an auth storage adapter so sessions persist across app restarts. The current `createClient` call has no `auth` options — add `auth: { storage: ... }` using an AsyncStorage or MMKV-based adapter.

### notification-scheduler Modification

Add a `dispatchEmailNotifications()` call after each notification scenario (deadline, stall, not-started). This is additive — existing push notification logic is untouched. The email dispatch is a separate `fetch` call to the `email-notifications` Edge Function.
